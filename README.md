# image-auto-save · 好友图片自动保存（Arona 功能插件）

收下**指定好友私聊**发来的图片，按 `昵称-QQ号-时间戳` 存进
`data/image-auto-save/image/`，可选把图片连「发送人：好友名(QQ号)」一起预览给别的私聊好友。
行为参照 mirai 版 `ImageAutoSave-YuLinMiraiPlugin`（`com.yulin.imageAutoSave`），并按需求
补上了那份插件没有的好友白名单与预览目标。

编译产物是 `image_auto_save_plugin.dll`，用户在**启动前**放进框架运行目录的
`plugins/image-auto-save/`，框架启动时扫描、握手、装配。插件没有 `main`，不能独立运行。

## 配置只有四项，四项都能在界面上改

GUI「插件管理 → 详情 → 配置」那一页只给**标量叶子**画控件，表与数组整格跳过
（框架文档 §12）。所以两个好友列表存成一串逗号分隔的文本，而不是 YAML 数组——
登记成数组的话你在界面上根本碰不到它，"在 GUI 里勾名单"这件事就结构上做不到。

| 配置项 | 界面控件 | 含义 |
| --- | --- | --- |
| `enabled` | 勾选框 | 是否开启。关着的时候收到图也不取、不存、不预览，默认关 |
| `friends` | 文本框 | 接收图片的好友列表，逗号分隔的 QQ 号。名单外的人发的图一概不存 |
| `preview_enabled` | 勾选框 | 是否启用发送给好友预览 |
| `preview_friends` | 文本框 | 发送给好友列表，每人一条「图片 + 发送人：昵称(QQ号)」 |

手改 `config/image-auto-save/arona.yml` 时两种写法都认：

```yaml
image-auto-save:
  enabled: true
  friends: '10001,10002'      # 也支持中英文逗号、分号、顿号、空格分隔，重复的号只留一次
  preview_enabled: true
  preview_friends:
    - 10003                   # 写成 YAML 列表同样读得进来
    - 10004
```

改完保存即热生效，不必重启；插件会在日志里把生效后的开关状态、目录与两个名单的人数报一遍。
填错（比如串里混进非数字）会明确报出是哪一个 token 不对。

## 没有的那些项，是刻意没有的

- **保存目录不给配置**：固定落在框架分配的 `data/image-auto-save/image/`。框架 §7 的规矩就是
  「插件不要自己拼路径」，目录接口由框架统一给。
- **群相关一律没有**：本插件只订 `BodyFilter::private("friend")`，群消息、临时会话的图都不进
  这一档，也不接命令。`meta()` 因此声明 `with_group_scoped(false)`——框架不再给它画
  「启用的群」那一格，`group_settings.<群>.disabled_plugins` 里残留的条目对它一律放行，
  GUI 与 `admin::set_group_plugin_enabled` 也拒绝对它写这一项（框架文档 §6、§13）。
  它同样不登记功能开关，免得在群功能清单里多出一排勾不动的复选框。
  全局停用走 GUI 的插件总开关（`disabled_plugins: [image-auto-save]`），框架连钩子一起收（§13）。
- **子目录模板、大小上限、去重、状态命令、可配的提示语文案都没有**：按"配置面只留四项"收掉了，
  需要哪一项再单独提。发给发送者那两句是固定行为、不占配置项，见下一节。

## 回执发给发图的人

每条处理完都**引用回复原那条图片消息**（mirai 的 `QuoteReply` 同一档，框架给的
`OutgoingMessage::quoted(消息 id, 文本)`），发回给发图的那个人：

| 情况 | 回什么 |
| --- | --- |
| 至少存成一张 | 「图片已保存」 |
| 有没存成的 | 再补一句「图片保存失败」，细节写日志（哪一级线索失败、为什么） |
| 一条都没存成 | 只回「图片保存失败」——绝不能回「图片已保存」，假回执比不回更糟 |
| 实现端没给消息号 | 照样回话，只是挂不上引用（不为了引用把回执整条丢掉） |

一条消息里几张图混着成败时回两句，不是每张一句。回执与预览都走框架统一发送口
`send_message`，所以出站钩子与黑名单都在这条路上（§9.1）。

## 落盘的文件叫什么

```
阿罗娜-10001-2026-10-16_21-45-53.915.png
└─昵称─┘└─号─┘└─────时间戳(毫秒)────┘└后缀┘
```

昵称过一遍清洗：`\ / : * ? " < > |` 与控制字符换下划线、连续空白折一格、结尾不留点或空格、
躲开 `CON`/`NUL` 这些 Windows 保留名、按 24 个字符截断。后缀**先按字节头嗅**
（png/jpeg/gif/webp/bmp），嗅不出来才照实现端给的直链或路径后缀猜，都没有兜底 `.jpg`。
mirai 那份比的是 HTTP 响应头的 `Content-Type`；这边字节已经到手，看头几个字节更准，
也不必为拿响应头去举 `wanting_headers` 旗。

同一条消息里几张图撞名时，写入用 `create_new` 往后排 `-1`、`-2`，
不会出现后一张悄悄覆盖前一张、而对方以为已经存过了。

## 一条图是怎么拿到字节的

各家实现端给的线索不一样，按四级回退，前一级的失败原因会一起写进日志：

1. **内联字节**（`data`）——框架已把 `base64://…` 就地解成字节，直接用；
2. **直链**（`url`）——`arona::runtime::http` 交宿主代发，插件不链接 reqwest（§14.1），单张超时 15 秒；
3. **本机路径**（`file`）——`std::fs::read`，`file:///D:/%E5%9B%BE/1.jpg` 这种写法也认；
4. **只剩 `file_id`**——向实现端调一次 `get_image`，回直链、回 base64、回路径都接住。

第 3、4 级要求 **OneBot 实现端与框架在同一台机器**；不同机时读不到路径，日志会直接写明
"多半是 OneBot 与框架不同机"。第 4 级的 `file_id` 只有给过它的那个实现端认得，
换实现端或跨账号都不保证还能取回。

预览带的是**原样的图片段**（直链、`file_id` 这些线索一并带回），有直链时不必把字节再上传一遍
（§19）；发送走框架统一发送口 `send_message`，出站钩子与黑名单都在这条路上，
没用 `api.send_private_msg` 那条协议层旁路（§9.1）。

## 收不到图时先查这几条

- 界面上的**总开关有没有勾**，`friends` 里有没有那个人的 QQ 号——两档都过了才会去碰网络。
- 只收**好友私聊**。群里的图、临时会话的图都不进这一档。
- GUI「插件管理」里这家插件有没有被停用；停用了钩子不再投递，任务也会被收掉。
- 下载与写盘都在后台任务里跑，钩子拿到消息就放行（`HookFlow::Pass`），
  不吞消息也不拦命令，所以机器人还会照常说别家插件的话。

## 发布三件事（框架文档 §22 要求写明）

```
适用于 Arona-rs 1.2.1（符号布局 10）
Windows：rustc 1.98.0，x86_64-pc-windows-msvc，--release，crt-static
Linux：  rustc 1.98.0，x86_64-unknown-linux-gnu，--release，cargo-zigbuild 按 glibc 2.17 基线链接
下载后放进 <框架运行目录>/plugins/image-auto-save/，重启框架
```

产物名 Windows 是 `image_auto_save_plugin.dll`、Linux 是 `libimage_auto_save_plugin.so`，
两者不能互换：插件被 `dlopen` 进宿主进程，装载前要比对工具链指纹，目标三元组就是其中一项。
Linux 那份按 glibc 2.17 链接，框架的标准包与 compat 包宿主装的是同一个 `.so`；这个后缀只影响
链接阶段，指纹里的 `target` 仍是 `x86_64-unknown-linux-gnu`，与普通 gnu 构建一致。

版本号以 `rust-toolchain.toml` 那一行为准；`.cargo/config.toml` 那两行 CRT 设置必须与框架仓库
逐字一致——它**只对 MSVC 目标生效**，Linux 目标故意没有条目：musl 静态下 `dlopen` 是空桩，
静态化了插件反而装不进去，所以 Linux 走 glibc 动态链接。对不上不是"握手失败"这么客气，
而是随机崩溃，所以框架会直接拒载。

框架 1.2.1 起只比布局号 + 工具链指纹，契约版本与 crate 版本都已从判据里删掉；但 1.2.0 及更早
编的插件在 1.2.1 宿主上会被拒载——指纹串去掉了 `arona/<版本>` 前缀，而比对是全等，重编即可。

## 开发

```bash
cargo build --release              # target/release/image_auto_save_plugin.dll
cargo test --release               # 28 条：名单解析、四项都是标量、命名清洗、后缀嗅探、撞名不覆盖、回执判据
cargo clippy --release --all-targets
cargo fmt --all
```

改一行代码就是"重编 dll → 拷进 `plugins/image-auto-save/` → 重启框架"这三步。装载成功的标志
是启动日志那三行（布局 10 / 契约 1.0.0 / 已装载 / 已启动），紧接着本插件报一行生效配置。
本插件没有跨调用状态，所以 `export_arona_plugin!` 直接交类型名而不是 `::default()`。

**这份 dll 要配布局 10 的宿主**（`HostBridge` 多出借字体字节那条 `fonts` 通道，框架文档 §22）：
先用改过的框架重编 `arona-rs.exe`，再放这个 dll；反过来，旧宿主会明确拒载它，
日志写「插件 ABI 布局版本不匹配：插件为 10，本框架为 9」。同一次升级里
petpet、bilibili、bluearchive 那三家也要用新框架重编，否则新宿主按 §22 拒载它们。
版本对得上号：0.1.1 只是随框架抬到布局 10 而重编，本插件源码零改动（它不绘图，用不上借来的
那份字体）；0.1.2 才加了回执——存成与否都**引用回复发图的人**，成与败各一句，见上面「回执发给
发图的人」那一节。布局号仍是 10，两版 dll 不能互换的是功能而不是握手条件。
